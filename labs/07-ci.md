# Lab 07 — Make review gates enforceable

**Time:** 45–75 minutes

[Course home](../README.md) · [Previous lab](06-docker.md) · [Next lab](08-observability.md)

CI repeats checks when code changes. Branch protection makes those checks matter.
Prerequisite: Lab 06 and a repository on GitHub; follow [GitHub setup](../docs/github-setup.md).

## Procedure

1. Read `.github/workflows/ci.yml`: `tests` checks Python behavior and documentation
   links; `container` builds and smoke-tests the image.
2. Read `security.yml`: `scan` fails on HIGH/CRITICAL findings. These are separate jobs.
3. Confirm all three jobs have run on your repository.
4. Apply the protected-branch settings in the GitHub setup guide using the actual
   check names reported by your first run.
5. Create `practice/ci-failure` from a clean `main` and repeat Lab 03's `all` → `any` fault.
6. Commit, push and open a clearly labeled **DO NOT MERGE — training fault** PR.
7. Inspect the failed test output. Confirm merge is blocked by the required check.
8. Restore `all`, commit and push. Expect tests to pass; scans may still need triage.
9. Close the practice PR without merging. Do not weaken branch protection for the drill.

## Release authority exercise

Configure the `training-release` environment, then run **Release rehearsal** from the
Actions tab on `main`. With required reviewers configured, it should wait for approval.
After approval it runs an ephemeral container, records the source/image identity in the
job summary, and removes the container. No public service is created.

If your account cannot enforce environment reviewers, record that gap. A workflow
referring to an environment name does not by itself create an approval requirement.

## Completion evidence

Keep the failed and corrected runs, branch-protection settings, and rehearsal summary.
Explain CI versus delivery versus deployment. Do not call the project protected until
a test PR demonstrates that the intended gate blocks merging.
